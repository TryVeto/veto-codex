# Work control

**Protect the outcome, not a stale plan. Capture feedback without turning every message into a new project.**

Use the existing Head, team and current work record. This method does not enqueue messages, alter host settings, start a goal or cancel a process. For an explicit goal-adoption request or a real blocked assignment, use [native state guards](../../references/native-state-guards.md) so the native action and title readback remain separate from the work record. Read [working boundaries](../../references/working-contract.md) and [the control protocol](../../references/work-control.md) only as needed.

For a repeated avoidable failure, use [decision and correction continuity](../../references/decision-continuity.md) to save the observed case, smallest repair and later retrieval check in the existing record. Do not turn the correction into a new standing process.

## 1. Separate delivery, intent and authority

The host controls when a message arrives. The message says what the user needs. The mandate says which actions are permitted. None implies the others.

Establish the latest actual goal, explicit pause/resume, current bet and checkpoint, pending operations and affected workers. Do not resurrect a historical pause after a later resumption, or treat an attachment, copied relay or plugin adoption as permission to resume. Resolve a material authority conflict before the dependent act; continue unrelated authorized work.

| Incoming request | Response inside the mandate |
|---|---|
| Status or explanation | Answer from existing evidence; do not change scope or restart workers. |
| A routine correction to current work | Batch with related changes at a suitable checkpoint; honor a specified deadline/dependency. |
| Evidence the current approach is wrong | Reassess now; change the affected plan when justified. Do not protect focus at the expense of truth. |
| A separate idea or next feature | Record as an option or proposed next bet, not automatically accepted work. |
| Explicit stop/pause or material active hazard | Stop initiating affected actions; use available supported controls, preserve state and reconcile in-flight effects. |
| Explicit new authorized assignment | Carry it through within its scope; an unrelated paused goal stays paused. |

A queued message may arrive before a multi-turn goal completes. Follow its named dependency, not an invented assumption that the entire goal is done. A steer may add evidence without changing acceptance. Tags such as QUEUE or STEER in prose are conventions, not host commands.

## 2. Make one disposition and preserve it

Before continuing a feedback batch, capture every annotation with a stable ID, original wording, screenshot/page context, interpretation or question, owner and observable check. Reload unresolved IDs after interruptions. Use [feedback coverage](../../references/feedback-coverage.md); a summary is not the original. Keep its target, user intent and disposition in the existing work record: **apply to current bet; after named checkpoint; propose next bet; superseded with reason; needs decision**. Distinguish observation, suggested solution, adopted requirement and authorized effect. Do not make a user fill out an intake form.

Batch related annotations. Preserve scope and meaning across the batch; do not broaden a local craft request to the whole product unless a demonstrated shared cause warrants it. Reproduce reported defects on the actual candidate. The no-decorative-eyebrows rule is adopted Veto policy; it is not a reason to delete functional labels or change the product direction.

A brief disposition is useful when timing or scope changes. Do not narrate every bookkeeping action. Receipt of feedback is not implementation. Return evidence when the correction is actually verified.

## 3. Steer the team, not just the chat

For an adopted change: update the current assignment revision, name what changes and what remains fixed, identify affected interfaces, and inform actual contributors through available channels. Stop conflicting superseded work; do not discard useful uncommitted changes or cancel unrelated contributors.

Before integrating a late return, compare its assignment revision and assumptions with the current contract. Preserve compatible work; recheck affected evidence. A worker saying done under an older instruction cannot silently restore a rejected direction. If cancellation cannot be confirmed, report that fact and fence conflicting writes where authorized. A cancelled client does not prove a server-side effect was cancelled.

For a risky or irreversible pending effect, use the host's actual stop/pause/approval controls. Never promise immediate cancellation from prompt delivery or assume a stop undoes a sent message, persisted mutation or disclosure. Reconcile before retrying.

## 4. Choose the right execution unit

Use an ordinary bounded turn for a critique, specific correction, question or unresolved choice. Use a goal for a substantial outcome the agent can pursue and verify over multiple turns. A learning goal is valid when it has a finite question and an honest stop; it need not pretend the implementation is already understood.

Shape only unresolved decisions with [product sense](../product-sense/SKILL.md): problem, appetite, solution boundary, rabbit holes, no-gos and proof. Then [make a goal](../make-a-goal/SKILL.md) without importing another organizational process. A clear authorized repair goes straight to execution.

Maintain one active delivery bet beneath the accepted vision. Preserve all existing acceptance obligations, including buyer funding; completing one bet is not completing the umbrella. A fresh bet is selected from current evidence. Continue inside an existing delegated umbrella when its mandate authorizes that sequencing and resources; otherwise return the next decision. Do not turn a queue of ideas into automatic future spending or silently narrow accepted scope.

## 5. Checkpoint and finish

Checkpoint at a meaningful joined result, decision-changing failure, required approval, current resource boundary or explicit user stop. Save candidate, evidence, remaining work, active assignment revision, pending effects and the next owner/action. A checkpoint is not a request for permission to do already-authorized routine work.

If the next attempt repeats an unchanged failed hypothesis, change the experiment, inspect the missing boundary or state the external dependency. If acceptance is met, deliver the exact candidate. If the route is defeated or its authorized allocation exhausted, preserve the result and return the re-bet decision; do not quietly renew the allocation or erase an accepted duty.

Use [the operator guide](../../OPERATOR-GUIDE.md) for message examples and current documented host controls. Do not claim those controls were used unless invoked and checked in the actual host.

For cross-session continuation use [start and resume](../../playbooks/start-and-resume.md); for an adopted manager steer use [manager return](../../playbooks/manager-return.md). A [checked handoff](../../references/handoff-record.md) verifies bytes, never permission to resume.
