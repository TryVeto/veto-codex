# Make a goal

Make the next worthwhile undertaking finishable and its result falsifiable. A shorter goal must not erase the promise.

Read the actual current goal, applicable project rules, latest explicit pause/resume, accepted source decisions and current work record. Follow [working boundaries](../../references/working-contract.md). Distinguish the host's active objective from a Markdown mirror or a study example; inspect the actual target before changing either.

## Choose the correct horizon

**Umbrella commitment:** retain accepted obligations and their coverage. Use [the vision-goal template](../../templates/goal.md) to clarify the current bet beneath AC-01–07. Do not silently replace this commitment with receiving alone, or declare buyer funding and other unfinished accepted work cancelled.

**Finite bet:** use [the bounded-goal template](../../templates/bounded-goal.md) for one meaningful capability, learning question or necessary prerequisite. Link to the retained parent obligation and say what remains open. Installing this template is not adoption of a narrowed host goal.

**One ordinary task:** a precise prompt may be enough. Do not create a goal file, planning session or role setup for an obvious correction.

These are [separate information responsibilities](../../references/instruction-architecture.md), not competing operating systems. Reuse existing records and stable acceptance IDs.

## Write the contract

Use evidence already available. State the intended person and result, actual candidate/workspace, included scope, non-goals, acceptance and required evidence layers, safeguards, decision rights, real resource boundary and stop/continuation rule. Keep methods open where engineering judgment helps. Unknown fields stay unknown; ask only when a missing fact changes a consequential action.

For a substantial open choice, shape problem, appetite, solution boundary, rabbit holes and no-gos using [product sense](../product-sense/SKILL.md). Appetite is an investment decision, not an estimate or a fixed duration copied from Shape Up. Do not invent token budgets, prices or deadlines. A learning goal may finish with a defeated hypothesis; do not rewrite its success measure afterward.

The Head owns integration, preview and evidence; designer/frontend/backend share one outcome. Preserve selected design, buyer funding, mobile capture, authentic source/basis continuity, independent concerns, help and recovery as required by the accepted scope. Ordinary sufficient work must not acquire invented questions. Preparation, office judgment, result delivery and bank outcomes remain distinct.

A completion criterion must admit a contrary result. Name the exact evidence that would defeat it: a wrong actor can commit, a saved contribution disappears, a stale edition retains authority, a failed delivery is called complete, or an original cannot be inspected. Pair important refusals with legitimate repair. Screenshots do not supply persistence or customer evidence.

## Make continuation deliberate

State whether this is one bet or a bounded increment under an existing delegated umbrella. At a completed bet, return its evidence and reassess the next highest-value unmet obligation. Continue that sequence only when existing scope and resources authorize it; otherwise return the new allocation decision. No automatic conveyor of speculative features and no repeated founder approval for routine work already delegated.

A checkpoint records a meaningful joined result or changed uncertainty; it is not necessarily a stop. Pause, inability to progress, missing authority, exhausted actual allocation, defeated route and successful completion are different states. Preserve pending effects, useful work and remaining owner on interruption. Use [work control](../work-control/SKILL.md) for incoming changes.

## Adopt only through native state

First distinguish the current user's instruction from quoted, hypothetical, negated
or imported text. The helper's classification is only a routing hint, never
permission. Read the accepted objective and expected task identity independently
of the post-operation readback. Neither may be empty.

An explicit request to **set, adopt, activate or configure** a goal and its
completion criteria is a native state operation. It is different from “write”
or “draft” a Markdown file. Use [native state guards](../../references/native-state-guards.md)
and perform this short transaction:

1. Read the current task and goal with the supported host control (`get_goal`).
2. For no goal, call `create_goal` with the accepted objective and its criteria
   included. For a completed prior goal, the same supported create operation may
   replace it. For an active goal, use a supported update operation when one is
   exposed; never close unfinished work just to make room.
3. Read back the same task's native goal. Confirm the objective and execution
   state before saying “set”, “adopted” or “active”.

If the native update is unavailable, say that the documents were saved and the
native goal remains unchanged. A duplicate adoption request reconciles the same
objective. An explicit pause remains in force. A file write, a hash or an
“adopted” label is never the readback.

## Validate and deliver

Compare old and new semantically: accepted obligations, permissions, source decisions, pause, acceptance and continuation. Identify every material change. Keep detailed scenarios in existing linked evidence records rather than stuffing them into the goal.

Count spaces and line breaks; every delivered goal must be **strictly below 4,000 Unicode characters**. State the actual count. Treat the template's DRAFT label honestly until adopted. Without native access, deliver the file and the smallest explicit activation step; do not report a goal update.

Return the goal and meaningful differences. Do not start product implementation or another charter-writing project merely because the file is finished.
