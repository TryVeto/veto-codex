# Review a prototype

Make the important product decision inspectable without the founder collecting screenshots or explaining how to use the app.

Read [the review protocol](../../references/review-protocol.md) and [pack contract](../../references/review-pack.md). Preserve the current [working boundaries](../../references/working-contract.md). Setup, review and repair are separate modes; a critique stays read-only unless repairs are already authorized.

## Prepare

Identify the exact candidate, actual served build, fixtures, task, roles, fixed constraints and supported endpoint. Reuse the canonical app; add versioned review materials, not a second maintained codebase. Prefer a commit plus explicit dirty snapshot identity where needed. Keep original, replay and visual-reference identities distinct. Preserve user work and the founder's saved case; an already-completed case cannot prove its earlier transition.

Identify the actual model/mode when exposed, client, execution host and evidence channel. Do not infer Pro execution from a subscription or effort label, or assume a saved image reached the reviewer. Unknown identity stays unknown; do not change pinned settings to fit this procedure.

Pin a small review request before collecting captures. List required journey states, not an indiscriminate screenshot count. Capture the first useful view, main action, meaningful error/correction/Help, saved receipt and next-role retrieval with the permitted browser. Include supported narrow states and material shared dependencies. Keep unvisited areas visible.

Keep neutral full-resolution images, task steps and evidence separate from founder annotations and builder explanations. Record candidate/scenario/role/state/viewport for each. Disclose inability to capture or execute a state. A chat screenshot about the product is not a fresh app capture. A localhost link is not portable across machines.

Inspect source, logs, screenshots and archives for sensitive data. Use declared synthetic fixtures. No credentials, real financial/identity documents or live recipients. A file name or automated scan does not prove sanitization. Never deploy or tunnel the app merely to get review access.

## Package

Use the existing tooling or the optional standard-library [review-pack helper](../../scripts/review_pack.py). It only reads explicit files, checks a separately pinned request/hash inventory and writes a new ZIP plus static index. Read `--help`; it runs no product, browser, model or upload. A COMPLETE pack is not a passing product review; PARTIAL material can support a bounded critique.

For ChatGPT Pro, attach a neutral brief and representative actual PNG/JPEG/WebP images directly, plus source ZIP or an accessible exact repository/commit reference. Include the indexed pack for detail. Do not assume image retrieval, ZIP execution, video playback or localhost access in the receiving host. Verify which material the reviewer actually accessed.

## Review

Give a fresh reviewer the [neutral prompt](../../templates/pro-review-prompt.md), fixed constraints, source context and candidate. Do not hide safety information. First form a grounded view without the founder's proposed fix where feasible; then inspect annotations/rationale and reconcile. Label prior opinion exposure. No role title creates independent evidence.

Try the real task without a click-by-click rescue. Judge usefulness, meaning, continuity, craft and dependability separately. Identify location, observation, consequence, smallest credible repair and required verification. Distinguish visible observations, source hypotheses, actually exercised behavior and missing evidence. No minimum bug quota, vibe score or fictional user validation.

If the required reviewer cannot operate this local app, use the existing authorized collector route: request one observation that distinguishes the leading explanations; receive actual images, actions, starting state and result; then judge that evidence. Do not invent a bridge, remote access, an upload or another worker. Without a transfer route, return the partial review and precise missing observation. Use the [observation record](../../templates/review-observations.md) only when needed.

## Close

The Head dispositions findings within actual decision rights; builders repair when authorized; a separate pass rechecks the changed candidate and relevant dependencies. Do not let the critic edit its own evidence into a pass. Reopen only for changed facts or material unresolved risk, not repeated taste.

Report review coverage separately from candidate health: a COMPLETE review can find a BLOCKER; a PARTIAL review can report NO BLOCKER OBSERVED only within its inspected scope. Neither is universal acceptance. Do not convert “not reproduced” into “fixed.”

Recheck the source/served identity at the end. Unexpected drift makes affected conclusions stale or unresolved until replayed; preserve the original evidence rather than relabel it. Return candidate, accessed evidence, scoped verdict, consequential findings and open gates. Keep technical acceptance, deployment permission and real-user benefit separate. Do not start a background review schedule without an actual configured mechanism.


Before final acceptance, give the reviewer the complete original feedback batch and require [source-to-acceptance coverage](../../references/feedback-coverage.md). Neutral first-pass review is not permission to omit annotations from the informed verdict. Keep unresolved or unreproduced items visible.
