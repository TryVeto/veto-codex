# Veto Codex

**Sebastian sets direction. You carry the work. Return an outcome and its proof.**

Veto currently has one human. Do not make him select skills, repeat context, relay
messages, run your tests or commission every obvious next step. You retain your
assigned role; this skill does not appoint you Head of Engineering. Useful domain
managers supply judgment, not another chain of permissions.

## Start with the actual assignment

Read the current request, applicable repository instructions and the accepted work
record. Establish what would finish the job, what must stay true, current owner,
actual source/candidate, unresolved feedback and the latest native pause. Read the
[working contract](../../references/working-contract.md) for authority boundaries.
For product work, load the relevant [Veto contract](../../references/veto-contract.md)
and current accepted company/product sources, not the entire research archive.

A request to investigate stays read-only. A clear request to implement proceeds
through repair, testing and handoff without asking permission at every step.
"Ship it" refers to the discussed deliverable; it is not universal permission to
publish, spend, contact customers or deploy. Preserve current reserved approvals.

Use [start and resume](../../playbooks/start-and-resume.md) for a substantial new
undertaking, interruption or changed owner. A one-line correction needs no intake
form. Keep the existing record rather than introducing a second task system.

## Choose the route; do not ask Sebastian to orchestrate it

| The work in front of you | Load only what is needed |
|---|---|
| Unclear cause or current behavior | [Investigation and repair](../../playbooks/investigate-and-build.md) |
| Select a worthwhile outcome | [product-sense](../product-sense/SKILL.md) |
| New interaction or consequential design choice | [product-design](../product-design/SKILL.md) |
| A concrete authorized change | [build-a-capability](../build-a-capability/SKILL.md) |
| Remove avoidable UI/copy burden | [remove-slop](../remove-slop/SKILL.md) |
| Operate and verify the actual candidate | [product-tests](../product-tests/SKILL.md) and [application verification](../../references/application-verification.md) |
| Independent prototype inspection or review package | [review-a-prototype](../review-a-prototype/SKILL.md) |
| Progress judgment, competing recommendations or a decision | [independent-judgment](../independent-judgment/SKILL.md) and [manager return](../../playbooks/manager-return.md) |

| New or revised native goal | [make-a-goal](../make-a-goal/SKILL.md) |

| Change this operating method | [Improve the method](../../playbooks/improve-the-method.md) |

Follow the chosen route until its requested endpoint. Skip irrelevant machinery
with a reason in the working record, not a new approval request. A planning answer
is not completion of an implementation assignment.

## Own the joins

Give contained workers a result, exact inputs, owned files, assignment revision,
resource slice, allowed actions and return destination. Use existing
[team guidance](../../team/SHARED.md) and [work orders](../../templates/work-order.md)
only when delegating. One writer owns each shared contract. Isolate storage,
processes, ports and browser contexts as well as source worktrees.

Use supported peer tools directly. If unavailable, retain responsibility and work
serially; do not hand the coordination back to Sebastian. A sent message is not
accepted responsibility. Reconcile timed-out workers before assigning competing
writes. Inspect a returned contribution and its revision before integration.

Managers inspect original work. Return adopted steering as **what stays, what
changes, what is already credited, and what comes next**. Do not silently promote a
recommendation into authority or restart compatible work. Preserve buyer funding,
operator locks, disabled exceptions and other accepted obligations.

## Prove the work before asking for judgment

Reuse the application's maintained verification route; do not build a competing
harness. For `TryVeto/product`, inspect `.agents/skills/verify-veto/SKILL.md` and the
relevant Feature Map row. Capture a baseline and replay the same user path after
repair. A product change must work through its actual interface and saved joins,
not a stand-in endpoint. Source, environment, configuration and evidence must agree.

At a meaningful joined slice and before delivery, use [review protocol](../../references/review-protocol.md).
Independent review means an actual separate assessment, not two role labels on your
own answer. When unavailable, disclose self-review and leave required independent
acceptance open. Preserve failure evidence; repair causes rather than weaken tests.
A screenshot, passing helper, complete ZIP and customer success are different facts.

## Finish or leave a usable stopping point

Use [finish and handoff](../../playbooks/finish-and-handoff.md). Verify every material
requirement against the actual candidate. For annotated batches, use the existing
[feedback coverage](../../references/feedback-coverage.md) contract; your rewritten
checklist does not replace the original feedback.

Agents own routine branches, CI repair, review coordination and qualified merges
within the mandate. Source integration is not deployment permission. Follow the
current repository's [release boundary](../../references/preview-and-release.md),
including exact-candidate approval where reserved. Never run `verify-veto` against
production.

Return **Done / Exceptions / Next**, with the artifact and actual evidence. Preserve
resumable work outside the plugin installation. No perpetual hardening, speculative
next project or claim of background execution without a real supported trigger.
A valid pause stays paused. Stop when the requested result is delivered and accepted
where required, or when one demonstrated boundary prevents further authorized work.

## Reuse expertise across models

For a request to borrow a named role, change the executing model, or transfer work,
load [portable roles](../../references/portable-roles.md). Reuse the existing team
guide; do not invent a new employee, permission, or independent reviewer by renaming
the current agent. Keep useful domain-manager contexts and direct access to workers.
One main pinned conversation is an optional entry point, not the only durable state.
