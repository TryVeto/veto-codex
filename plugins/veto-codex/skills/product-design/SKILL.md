# Product design

Resolve the person's task, then make its actual execution excellent. Read the [working contract](../../references/working-contract.md) and [Veto contract](../../references/veto-contract.md) as needed.


## Own the first mile and the last mile

Apply [Stripe-inspired whole-product craft](../../references/stripe-operating-system.md) to entry, setup, examples, language, errors and handoff—not only the center screen. Form an artifact-first view before reading the founder's diagnosis when possible; preserve hard constraints. The designer is accountable for a point of view carried into the actual implementation, not a collection of attractive options.

Use [the review protocol](../../references/review-protocol.md) at the first integrated slice and final handoff. If a neutral walkthrough needs explanation to find the main action or distinguish people/accounts, fix the underlying organization rather than adding more introductory copy. For sample-input design and rehearsal, load [sandbox practice](../../references/sandbox-and-local.md).

## Inspect and preserve

Find the exact route, screenshot, file or design node. Identify the starting candidate, current content, components, design decisions and permitted changes. A named but unavailable image is not a usable edit target. A visual reference does not establish hidden behavior or authority. Preserve successful decisions and user work.

Use the supported browser/design tool; inspect the returned render, not only source. When unavailable, work at the available layer and mark visual verification missing. Do not create a separate attractive demo as evidence that the saved product works.

## Choose a coherent interaction

Name the person, trigger, object, useful endpoint, fixed decisions and open axes. On an open structural choice, compare two or three genuinely different arrangements using the same representative material and states. Choose one for the relationship it makes clearer. Do not combine every option. On an approved reference, skip exploration and reproduce the relevant design within scope.

Learn a specific property from each reference: source adjacency, density, hierarchy, correction or motion. State what must not transfer: payment authority, irrelevant navigation, claims or a new identity. Distinguish service, engine and surface. See the [surface proposals](../../references/surfaces-and-first-feature.md) when architecture is the actual question.

Before drawing a consequential action, define actor + object/edition + prerequisites + effect + confirmation + recovery. Give the qualified reviewer evidence and disagreement, the participant one recognizable contribution, and a waiting person a true owner/checkpoint rather than a manufactured button.

## Build alongside engineers

Agree state and command contracts with frontend/backend early. Specify normal, loading, empty, permission-limited, changed-basis, error and completion states the chosen task can actually reach. Design correction, Help/Back, keyboard and return-later as part of the main experience. Use long names, full identifiers, dense sources and explicit synthetic fixtures rather than easy content that conceals the problem.

Stay through implementation. Review the working candidate as joins arrive; do not hand over a screenshot and disappear. Reuse existing components where their meaning and behavior match. A local design does not justify a new design system, font family, or dependency stack.

## Change shared conventions only when the task needs them

For shared tokens, components or form/status patterns, use [the small design-system contract](../../references/design-system.md). Separate foundations, primitives, patterns and domain meaning without making four packages. Prove one workflow and representative consumers; no catalog, token compiler or palette migration by default. Existing dedicated components can be correct; consolidation must preserve their actual contract.

## Finish the craft

Put question beside basis, consequence beside action, task beside owner. Group by meaning; use typography, alignment and proximity before extra containers. Remove repeated orientation before shrinking body text. Preserve Veto's selected identity. No decorative eyebrows/kickers/overlines; preserve functional labels, status and disclosures.

Use stable semantic color, readable hierarchy, deliberate imagery and restrained motion. An ordinary convention is acceptable when it fits; novelty and an anti-AI aesthetic are not acceptance criteria. Essential content must not wait for an entrance animation. Respect reduced motion.

Inspect actual desktop and narrow composition, long content, source reading, keyboard/focus, zoom/reflow, contrast, errors, saving and recovery against the project's accessibility target. A screenshot or automated scan does not certify the whole experience. Compare before/after with the same content and state.

Return the exact artifact or implemented changes, the decisions made, what was preserved, checks performed and missing evidence. A proposed or agent-rehearsed interaction is not observed customer comprehension. Use [product-tests](../product-tests/SKILL.md) when formal candidate acceptance is the assignment.
