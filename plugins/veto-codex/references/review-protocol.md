# Product reviews the team owns

Review the work before explaining the work. The default is a direct first-pass walkthrough, not a meeting, a presentation or another department. This protocol operationalizes the study's whole-product care and the later publicly described “walk the store”/friction-log practices. It is a Veto adaptation.

## Trigger reviews at meaningful joins

Run a review when a substantial journey first works, before an integrated handoff, after a material shared-component/state/copy change, or when feedback reveals a recurring class of error. A small isolated edit gets its relevant focused check. Do not reopen all screenshots or launch reviewers after every keystroke. A cadence requires an actual configured runner and authorization; a Markdown schedule is not automation.

## Ownership

The Head owns the candidate, review request, preview health and disposition. The designer owns task structure, language and craft; frontend owns interaction/accessibility; backend owns persisted truth and recovery. An available separate verifier starts read-only against the same exact candidate. Research and data join only for a named unanswered question. No founder screenshot collection, role switching or message routing should be required for routine local review.

Give each worker the agreed task, hard constraints, original evidence and its write boundaries. Give the critic a neutral first pass before the builder's explanation. Keep mandated safety and domain context visible. The critic records evidence; it does not edit the candidate or silently change its acceptance. The builder fixes; another pass verifies. Without a separate worker, label self-review.

## Prepare and use the review pack

Use [the review-pack contract](review-pack.md). Pin one candidate and one request. Source identity, served build, fixtures and captures must agree—or the mismatch remains an explicit limitation. Keep the known-good review instance separate from destructive restart/fault tests. Never open a tunnel, remove authentication or switch to a prohibited browser to make review convenient.

An independent reviewer receives task-based scenarios, not a click tour. First try the actual product using the permitted browser. If access is absent, inspect available images/source and mark the result as partial; do not invent an interaction pass. A localhost URL from another environment is not a portable preview.

Walk each materially changed supported episode: entry; next useful act; consequence; interruption/correction or Help; resumption; personal stopping point; next person's retrieval. Observe original sources, permissions and saved state at their appropriate test layers. Do not use direct database injection to pass the transition under test.

## Keep observation and judgment connected

Use a brief identity line: actual model/mode when exposed; client; execution host; evidence received. A model subscription is not proof of a selected mode. A local path or image filename is not transferred evidence. Keep unknowns visible and use the actual authorized route; no new bridge, paid API call or hosting is implied.

Preserve source/build identity at the start and end. Record whether the case was fresh or resumed, its fixture edition, browser context, actor and storage/provider modes. Seed prerequisites, never the transition under test. Do not reset original user state to manufacture a clean replay. Isolate replay state or serialize observation; different ports alone do not isolate cookies. Unexpected drift invalidates affected claims, not every unrelated observation.

When observation and reasoning occur in different environments, the reviewer asks for a bounded check: **finding/question → candidate and starting state → permitted action → result that distinguishes explanations → returned evidence**. The collector returns actual actions and observations, including failure, through the supported handoff. The reviewer must inspect the images or results, not only the collector's conclusion. Test the strongest plausible alternative before declaring a disputed cause. Stop at a supported decision or an explicit evidence gap, not endless screenshot requests.

Use the existing issue/pack or [observation record](../templates/review-observations.md). Mark a finding reproduced, contradicted, unresolved or stale. A second pass by the same agent is self-review; extra role names do not establish independence.

## Coverage precedes acceptance

For a feedback batch, use [original-feedback coverage](feedback-coverage.md): inspect all actual annotations/context, map their complete meanings to acceptance, preserve questions and supersessions, and reload unresolved IDs after interruption. A neutral first walkthrough can precede annotations; final acceptance cannot omit them. Missing items or originals keep the batch open even when selected tests pass.

## Apply this ordered review

1. **Worth doing:** Does it remove or materially improve a real job? Does another surface or obligation earn its cost? Unknown demand remains a hypothesis.
2. **Meaning:** Does the person understand the object, next act, consequence, relevant evidence and stopping point? Are role/account labels semantically distinct?
3. **Continuity:** Does the same work survive correction, Help, role transfer and reopening? Are receipts and current queues truthful?
4. **Craft:** Is the ordinary first useful view obvious, coherent, readable and accessible at desktop and narrow widths? No decorative eyebrows; remove framing before shrinking type.
5. **Dependability:** Does the relevant ordinary success, refusal, uncertainty and authorized repair hold in the actual service? Can the next owner use the delivered result?

An integrity failure blocks the affected acceptance. A source hypothesis is not yet a reproduced defect. An advisory preference is not a release blocker. No weighted overall beauty score can offset false completion.

## Record friction while it happens

Use the existing issue or [small friction record](../templates/friction-log.md): candidate, scenario/state/role, observation, evidence locator, consequence, correction, owner, recheck. Record pause/help/coaching and inconvenient observations. Do not fill a minimum issue quota. Distinguish observed, inferred and unknown.

Group observations by cause. Repair the largest consequence first, then batch local craft corrections. Recheck changed dependencies on the new candidate. Keep the first failure and its actual subsequent result; do not rerun until lucky or quietly replace an approved visual baseline.

## Turn these screenshots into transferable tests

The supplied screenshots show founder annotations and the Head's response, not a fresh runnable product audit. Use them as reported friction and candidate cases:

- At a file awaiting seller contribution, can the officer find the next action—such as creating the seller link—before unrelated review administration? When the file is already submitted, does the next action change appropriately? Do not hardcode one button for every state.
- Can the officer distinguish the seller/contributor, the qualified receiving reviewer and any separate handoff recipient? Avoid labels that confuse a user login, a party and a bank account. Preserve necessary authority distinctions rather than hiding them behind one person field.
- Where the sandbox asks for input, are safe scenario-valid sample values available beside the fields, with explicit Copy or Fill actions where appropriate? Do not require private founder knowledge or insert unreviewed sample values into live work.
- Do active tab, Back, Help, errors and saved values preserve orientation and context? Is all decorative eyebrow treatment removed without removing functional labels?
- Where both journeys belong in the same escrow file under the accepted model, can the reviewer navigate seller collection and buyer funding without losing that file identity? Do not merge the meanings of the two journeys or assume a migration is needed from this screenshot alone.

## Close the review without a perpetual committee

The Head dispositions every material finding: fixed and rechecked, accepted tradeoff by its actual decision owner, outside current scope with retained owner, or unresolved gate. Ready-for-review, technical acceptance, production approval and customer benefit are different verdicts.

Stop when required criteria are met and remaining observations have a justified disposition. If repeated rounds add no new evidence, change the test/hypothesis instead of spawning more critics. Send Sebastian one decision-ready exception only when his actual authority or unavailable knowledge is needed. The complete report can live in the pack; routine progress need not consume his attention.
