# Work control: attention, execution and authority

This is Veto's proposed operating convention, informed by the supplied Shape Up, goal and AGENTS studies. It is not a new scheduler, a claim about Stripe's internal tooling, or permission to change the current mandate. The [source map](../research/WORK-CONTROL-SOURCE-MAP.md) separates source recommendations from documented host behavior.

## Three independent questions

**When is input delivered?** Current OpenAI documentation distinguishes steer into the current run from queue for the next run. A goal may span runs. Therefore a queued message should name a milestone when its work must wait beyond the next run. [Prompting documentation](https://learn.chatgpt.com/docs/prompting)

**What is being requested?** Status, evidence, a suggestion, a correction, a decision and a stop are different intents. A queued new feature is not necessarily adopted scope. A steer containing a reference does not necessarily authorize a redesign. Classify using the user's words and current context, not a rigid keyword parser.

**What is permitted?** Authorization still comes from the current mandate and actual host rules. Delivery timing, model confidence, a role title and an attachment cannot expand it. Goal mode retains the existing sandbox and approval policy. [Long-running work documentation](https://learn.chatgpt.com/docs/long-running-work)

## One working record, not another project manager

Keep one active delivery bet, its assignment revision and its next meaningful checkpoint. Put other input in the existing record, not a new database. A short section can hold:

```text
Now: accepted outcome, owner, revision and next check.
Evidence: exact candidate and observations; unresolved claim.
Inputs: source → intent → apply / after checkpoint / proposed next / superseded / decision.
Continuation: delegated sequence or stop at this bet; retained parent obligations.
Recovery: pending effects, paused work, actual owner and next action.
```

Those are information needs, not five mandatory files. An obvious one-line correction may need no persistent queue entry. Accepted customer obligations and integrity incidents cannot be deleted as stale ideas. Optional suggestions can be retired with their reason when worth retaining.

Do not confuse the **host message queue**, the **development work list**, and Veto's **customer obligations**. Reordering the first does not reprioritize the second or discharge the third.

## Queue ordinary feedback; interrupt for changed reality

Queue a batch when it can wait without worsening the current result: spacing, copy clarity, consistency, a proposed next experiment. Name the affected candidate and surface when possible. The Head handles routine interpretation and gives a brief disposition only when needed to prevent a misunderstanding.

Steer when continuing under the old information would waste consequential effort, violate a requirement or cross a boundary: wrong user, wrong primary job, incorrect source, false save, emerging hazard, a revoked authorization. A small message can justify an immediate correction; a large attachment can still be later reference material.

For a current bet's accepted quality gate, after-checkpoint does not mean after acceptance. Remove prohibited decoration and resolve relevant comprehension failures before declaring that bet accepted. Optional unrelated polish must not displace a broken saved journey.

For an urgent stop, use the actual host stop/pause control rather than queueing a message. Then verify the observed state and any affected workers/processes. A process or external operation may outlive the client; preserve and reconcile its outcome before resumption. Stop only owned/affected work and keep user data.

## Reduce revision churn

An adopted steer increments or otherwise identifies the current assignment revision in the existing record. Name the preserved constraints and changed acceptance, if any. Only the authorized owner may change acceptance; the builder cannot lower it to pass. Notify affected contributors and re-evaluate returns made against older assumptions. Compatibility is judged by the actual contract, not by a timestamp alone.

Example: a reviewer discovers seller collection and buyer funding refer to different jobs in one file. Correct the shared interface with its owner; do not have each specialist independently rename objects. A later frontend return must not restore the old conflation. Keep legitimate buyer behavior intact.

Examples are synthetic work-control exercises, not newly reproduced Veto failures.

## A bounded bet can sit under a larger commitment

Keep the full accepted vision and AC-01–07 traceable. Select one current capability with a proof sentence. Record what this increment satisfies, preserves and leaves open. Do not mark accepted unfinished obligations as cancelled or make them disappear under out-of-scope wording.

Before starting another bet, inspect what the last one taught. An already authorized umbrella may delegate this selection to the Head. A one-bet assignment does not. Neither case justifies asking Sebastian to approve every reversible implementation choice. Only a new commitment, reserved action, material changed scope or exhausted authorized allocation needs the corresponding decision.

Appetite means what the problem is worth investing, not a forecast of how long it will take. Use actual limits; leave unknown allocations unknown. A checkpoint can expose the next allocation without inventing a token minimum or a fixed six-week cycle. Cut optional breadth, not privacy, meaningful completion, necessary recovery or accepted duties.

## Diagnose drift before writing another instruction

Repeated tiny patches may indicate an unclear bet, a broken environment, missing sources, review congestion or a poorly routed skill—not insufficient adjectives. First inspect which instructions actually loaded, what the agent attempted, and what evidence changed. Fix that boundary. Measure unexpected founder intervention, integrated completion and later defects; do not promote helper-test counts or token burn into evidence of product sense.

## Capture is not closure

Every annotation in a batch needs its original wording/context and a stable ID in the existing record; timing can still wait for a named checkpoint. Follow [feedback coverage](feedback-coverage.md). Preserve repeated occurrences and explicit supersession. On resumption, reload unresolved items from the whole undertaking, not just the latest message. Reconcile the active plugin path/version and actually loaded guidance before diagnosing “ignored instructions”; a downloaded ZIP does not identify a running worker.

## Preserve the requested delivery stage

A runnable prototype, source review, branch preview, production assessment and
production activation are different endpoints. Reconstruct the requested medium
and stage before resuming; do not substitute an easier artifact or silently advance
to a more consequential one. “Implemented,” “verified,” “accepted,” “deployed,”
“enabled,” “announced” and “used” each need their own scope and evidence. They are
not an automatic sequence of permissions. Use [the delivery boundary](preview-and-release.md)
when the handoff crosses environments. Advice or a status answer does not start a
mission, and a finished checkpoint does not erase the full commitment.
