# A rehearsal that teaches the product

Derived from the supplied `sandbox-experience`, `local-development`, engineering and design skills, and the Stripe study's test-environment chapters. This does not authorize any production activity.

**Remove the danger, not the meaning.** Begin close to the task with one recognizable synthetic episode and a useful inspectable result. Keep actual consent, authority and recovery distinctions. Simulation may remove risk; it must not silently remove the decision being evaluated.

## First-use contract

The person can identify the sandbox, choose an intended role, find scenario-valid sample inputs where requested, perform the task, inspect its result and recover a relevant failure without a private briefing. Disclose preseeded state. Seed prerequisites, not the final transition being tested.

Keep a persistent functional Sandbox indication; it is not a decorative eyebrow. Show Copy sample or Fill with sample only where it genuinely reduces setup. Use the current fixture's exact values and explain their simulated effect. Never invent supposedly valid wire instructions, real-recipient contact details, working provider credentials or bank login codes. Sample data is not a user profile or evidence of ownership.

Keep production input separate. Enforce the test/live boundary in actual server/adapters/permissions; a banner or client flag alone is not isolation. No hidden live fallback, real messages, checks, money movement, or paid resources. Any authorized provider sandbox needs its own test credentials, supported operations and known permitted costs.

## Scenario and state

Map the shared case, request, question/source/instruction editions, actor and resulting record as needed. Role switching changes perspective, not approval, data reset or accepted responsibility. Keep seller receiving and buyer funding distinct even when they share an escrow file.

Classify each boundary as shared real implementation, simulated under an explicit rule, represented only, or absent. A scripted ideal answer must not be called model performance. A local result must not be called external delivery. Persisted work is only as durable as the actual storage scope tested.

Test ordinary sufficiency, one meaningful failure and valid repair. Allow inspection of complete sources, contrary material, correction, Help, leaving and return. Preserve input as actually promised. Unknown save outcomes reconcile the original operation. A failed notice retries the notice, not the judgment. The output carries its fictional provenance with it.

## Local readiness is part of the experience

Start with one question: given this actor and state, which action should produce which result without which forbidden effect? Inspect the actual repository, revision plus relevant dirty/untracked changes, runtime, authoritative lockfile for this path, lifecycle commands, actor and storage. A listener is not journey readiness. Verify sign-in, read, edit, save and reopen where the selected claim depends on them. Identify the process actually answering the browser, not merely the branch in the editor.

Read unfamiliar scripts and relevant setup hooks before execution. Use the existing setup and action interface. If package metadata, setup notes and CI use different installers, inspect the actual path and its reason before changing anything; do not choose npm or pnpm by counting mentions. Historical repository observations are leads, not today's executable contract. A missing optional integration blocks its check, not independent local work; never replace it silently with an always-successful mock.

Use only the lifecycle operations this task needs. These are required meanings, not commands the plugin claims exist:

| Operation | Observable contract |
|---|---|
| Setup | Uses the correct pinned toolchain; repeating it preserves useful work and reports incomplete prerequisites. |
| Start | Reuses or starts owned processes; reports the actual URL/build; reaches required capabilities within a bounded wait. |
| Status / doctor | Inspects without mutation; distinguishes ready, starting, degraded, failed and unknown as relevant. |
| Scenario / verify | Establishes a named synthetic starting state; exercises the claimed behavior; retains failures and evidence. |
| Reset / stop | Names exact owned targets and lost work; never deletes data implicitly or stops another worker's process. |

Map these meanings into maintained repository commands before adding wrappers. Build a thin wrapper only for a demonstrated repeated failure; do not introduce a platform, task runner or broad dependency migration to fix one setup problem. The plugin itself starts no server and promises no background uptime.

### Use two evidence loops

Use the fast development loop for iteration and focused behavioral checks. Qualify the packaged target runtime when the change affects runtime APIs, bindings, server execution, packaging or another required acceptance boundary. A development-server pass is not a packaged-runtime pass. Do not run the full production-style build after every small visual edit, or skip a required final gate because the fast loop passed. Record which loop actually produced the evidence.

### Protect the review workspace

Worktrees isolate source, not databases, queues, object stores, ports, browser sessions or external accounts. Cookies are not isolated merely by using different ports. Establish owned resources and suitable permitted browser contexts before concurrent stateful work. Keep implementation, stable review and destructive replay separate where they would interfere; this is an ownership boundary, not a requirement to create three permanent environments.

Do not replace the review candidate, reset the founder's case or stop its server while it is being inspected. Promote a new local candidate deliberately through the existing authorized route and identify changed evidence. If resources cannot be isolated, serialize the conflicting work. A frozen HTML file is not a frozen backend or browser state.

Diagnose before restarting: intended URL → listener/process → running build → auth/config → store/worker → application effect. Use bounded observable readiness, not unexplained sleeps. Reconcile an uncertain action before replay. A broken required origin is a missing gate, not permission to bypass it with another browser or weaker access.

For an environment repair, finish by recreating the selected journey with the documented route and a fresh authorized operator or clean recreation where available. State which was actually checked. Preserve setup time and manual intervention when comparing improvement; do not substitute a larger fixture catalog for one reproducible job.

## Reset and return

Reset names the owned scenario scope, warns about lost work and leaves unrelated work untouched. Do not silently reset on role switch. Reopen after the promised interruption and inspect exact saved identifiers and values. A resettable demonstration and a saved local service may both be useful, but their claims are different.

For review, capture the exact rendered states plus task steps and truthful evidence. Sample inputs belong to the fixture, not source documents from a real customer. Inspect images, source archives, traces and logs for sensitive material before sharing; textual checks cannot sanitize images.

## Browser preflight before the first navigation

For Veto local UI tasks, read the installed browser's local-development guidance before the first navigation. Use the project's approved loopback-only HTTP preview; do not initiate `file:` navigation. Serve only the intended application/sandbox directory through the existing inspected lifecycle. Establish owned process/build/state, then open the exact HTTP target in the permitted browser and verify a visible page plus one responsive control before substantial implementation. This is Veto's preventive workflow, not a claim that every host rejects file URLs. It does not lift an existing denial. The plugin itself starts no process.

Record the exact tool, origin, candidate, operation, observed result and enforcing component when known. Distinguish unsupported URL scheme, site permission, auto-review, listener failure, wrong/stale candidate, test-session/auth condition and application defect. Unknown enforcement stays unknown. Do not generalize one rejected URL to ‘browser unavailable’ or infer an auto-review problem from any denied request. If permission is already enabled, do not broaden it speculatively.

On a policy denial, stop that access path and honor its stated scope. Do not copy/rehost the denied content or switch tools to bypass it. A harmless separate diagnostic's success is not an override. Preserve the denied-content gate and the specific support/permission action; continue only independently verifiable authorized work. Do not accumulate dependent UI scope while its inspection remains impossible. A build, HTTP response or unrelated Hello page does not close the actual target's rendered gate.

Repeat preflight when server, candidate, origin, session or permissions materially change—not before each click. Keep restart/fault tests off the review instance. See [diagnosis and approval](diagnosis-and-approval.md) for ambiguous effects and the inactive reviewer-prompt clarification.

## Local-start fast path

For an authorized request to start an existing local app, resolve its actual
checkout, configured origin and maintained launcher. Inspect the launcher and
relevant environment loader before first use; do not replace a specialized runner
with a generic framework command. Reuse a matching owned ready process, or start
it through the supported lifecycle. Leave it running for the user's requested
use, retain retrievable logs and a stop route, and return the actual URL.

Keep this bounded: process alive and expected response from the intended app,
plus dependencies required for the requested use. A sign-in redirect or open port
is not proof of a protected journey. Browser interaction is required to claim that
journey works, not for every simple launch. Do not run the full release suite,
reinstall everything, follow logs indefinitely or build a new supervisor to start
an already-working app quietly.

Inspect effective configuration provenance without printing secrets. Preserve
custom loader/allowlist rules; do not create .env.local by habit or expose private
values through public variables. Restart or rebuild an owned instance only when
that setting requires it. An open container application does not prove its runtime
service is ready. Follow the actual dependency failure rather than reopening an
application window or resetting data.

A fixed callback/origin is an integration constraint: do not silently choose a
new port when that would break authentication. Identify an occupied listener's
owner; coordinate or report the conflict, never kill by port. Historical source
paths, launch commands, ports and database numbers are discovery hints, not active
configuration. No new launcher is included in Veto Codex.

For a stale-edit complaint, distinguish a wrong candidate, server-source update,
new-route discovery, browser HMR and configuration uptake. A reload displaying new
HTML does not prove no-reload HMR. Reproduce before changing a bundler; any fallback
stays local, justified and removable. A local API workbench, if explicitly requested,
needs development-only admission, normal API protections, constrained paths and
safe text rendering—not an arbitrary-URL proxy. Timeout or cancellation does not
prove that a server-side write was undone.
