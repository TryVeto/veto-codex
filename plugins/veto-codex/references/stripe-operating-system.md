# Stripe-inspired operating system

**Take responsibility for a useful customer capability. Make it excellent. Learn from actual use.**

This is Veto's adaptation of the supplied *How Stripe Ships* and public Stripe accounts, not an official Stripe handbook or a guarantee of Stripe's results. The study distinguishes documented history, interpretation, and proposed adaptations; retain those distinctions. Later practices do not become first-year rituals. [Evidence and adoption map](../research/STRIPE-SOURCE-MAP.md).

## Principles expressed as decisions

| Practice to borrow | Veto behavior | Evidence left behind | Distortion to reject |
|---|---|---|---|
| Start with users | Inspect a real permitted attempt or exact available artifact. Name the work the person wants finished and their competent alternative. | A sourced obstacle and the next discriminating test. | Invented personas, friendly praise, or founder conviction as demand. |
| Make the whole thing well | Design, engineering, copy, setup, errors, help, and handoff form one capability. The designer stays through the working build. | Same-job walkthrough and a useful result. | Beautiful screens wrapped around an unfinished service; a mandated Stripe visual identity. |
| Move urgently on what matters | Attack the consequential dependency first; integrate before polishing disconnected pieces. Choose substantial work when the outcome requires it. | A shorter path to the next useful result, not a larger patch count. | Token quotas, unbounded swarms, or cutting controls to appear fast. |
| Improve tomorrow's speed | Turn recurring explanation and observed defects into a component, fixture, regression or current runbook. | A second person can repeat the task without private rescue. | A platform or process rebuild before demonstrating recurring friction. |
| Collaborate without territory | One outcome owner, stable specialties, direct interface decisions, no orphaned joins. ## The working loop

**Observe → shape → build together → walk the product → repair → verify → deliver within authority → learn.**

Use one existing work record. It should answer: user/job; evidence and alternative; complete scope and non-goals; owner and decision rights; acceptance; next checkpoint. A small edit needs the applicable few lines, not eight documents.

Choose the unit by the user's result. “Seller corrects, submits, leaves; the officer retrieves that exact submission” is a capability. “Frontend done” is a contribution. Build the ordinary sufficient route first; do not manufacture extra checks so a demo looks consequential. Preserve buyer funding and other accepted obligations while sequencing one primary bet.

At the first working join, operate the actual product. Record friction before discussing how clever the implementation is. At the final candidate, replay the changed path plus material shared dependencies and recovery. A field proof has its own permission, denominator and endpoint; an agent rehearsal is not a customer observation.

## Writing enables ownership, not universal approval

Keep current decisions searchable with their reason, evidence and reopening condition. Distinguish decision owner, consulted expertise and informed observers. Visibility creates no new veto or access right. Keep sensitive data and personnel matters within their permitted audience. Do not copy Stripe's historic email visibility into indiscriminate disclosure.

The Head decides reversible in-scope implementation tradeoffs. A reviewer can block a **technical acceptance claim** with a reproducible mandatory failure; a preference is advisory unless it is an adopted product constraint. Sebastian retains reserved scope, commercial, data and release decisions. A blocked external transition does not stop independent authorized work.

## Support is product input

Inspect originating feedback when available. Classify an intervention: needed domain teaching, avoidable friction, missing capability, or intended professional/service work. Fix the transferable cause. Do not hide founder assistance inside a success rate, and do not automate a required professional decision simply to remove a person.

One substantive correction should improve the next attempt, not merely produce a polite response. A new rule belongs in the smallest reusable place: component, fixture, acceptance case, or calibrated example. Avoid appending every complaint to every skill.

## What not to copy

No automatic six-week cycle, all-hands, org hierarchy, email firehose, whole-company dashboard, fresh PRD per fix, or Stripe payment capabilities. No importing another company's branding, customer claims, contract rights, assets, or credentials. No promising that these practices cause startup success. Keep the mission ambitious and the current undertaking exact.

For independent challenge use [judgment](independent-judgment.md). For review execution use [the review protocol](review-protocol.md). For safe self-serve rehearsal use [sandbox and local practice](sandbox-and-local.md). Load only the part that changes the current decision.

## Automation belongs in the existing execution path

Stripe's indexed 2026 Minions account also describes deterministic linting inside an agent development workflow. The narrow transfer is to run established mechanical checks rather than ask a model to remember them. For Veto, keep judgment in the agent and stable checks in the existing scripts/runner. This plugin adds only explicit local helpers; it does not install Minions, a scheduler or a parallel platform. The partial-source limit is recorded as W15 in the source map.
