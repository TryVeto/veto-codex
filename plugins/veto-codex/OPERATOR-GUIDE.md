# Queue, steer and finish a goal

Host-interaction reference retained from 2026.9.1107 · 11 September 2026.
The current operating agreement is [GUIDE.md](GUIDE.md). Inspect current host controls before using the dated UI/shortcut descriptions below; this release does not revalidate them.

**Shape the uncertain choice together. Let the team execute a bounded goal. Review evidence at meaningful checkpoints. Queue ordinary feedback; steer when current work should change.**

This is a Veto recommendation derived from your supplied studies. Host mechanics below are separately attributed to current OpenAI documentation. Nothing here changes your running task, settings or permissions.

## 1. Queue and steer answer a timing question

OpenAI documents **Steer** as adding input to the current run and **Queue** as saving it for the next run. Desktop exposes the default under **Settings → General → Follow-up behavior**; queued messages can be edited, reordered, sent or deleted above the composer. The documented CLI shortcuts are Enter for steering and Tab for queueing; use the desktop setting's displayed shortcut rather than assuming it is the same. [1]

**My recommendation is Queue as your default.** Your feedback should be easy to capture without turning the Head into an implementation assistant waiting for another annotation. This is a recommendation for your workflow, not a claim that the setting has changed.

A queued message is not guaranteed to wait for the entire multi-turn goal. Name the dependency when that matters: after this saved-journey checkpoint, before acceptance of this bet, or propose for the next bet. The native message queue is not your durable development backlog.

| Situation | Best handling | Example wording |
|---|---|---|
| Useful polish that can wait | Queue one related batch | “After the saved-journey checkpoint, tighten these labels and spacing before accepting this bet. Preserve the chosen layout and state model.” |
| Wrong primary action or premise | Steer current work | “Steer: this actor came to create the seller link, not administer the review. Make that next act clear. Keep the accepted permissions and other roles.” |
| A new feature idea | Queue as an option | “For the next-bet decision: assess whether a saved filter removes a real repeated task. Do not add it to the current scope.” |
| Unsafe or invalid pending action | Stop/pause through the host, then reconcile | “Stop the affected work. Do not send or retry. Preserve the candidate and identify any in-flight effect before resumption.” |
| You only need an explanation | A side/read-only question from existing evidence | “Summarize the current bet, latest verified checkpoint and remaining decision. Do not alter implementation or resume paused work.” |

These are message examples, not new commands. A typed QUEUE prefix does not itself select the host's Queue behavior. Prompt delivery is not guaranteed cancellation of a tool already executing; use actual controls for an urgent stop and check what happened afterward.

## 2. Give feedback without becoming the dispatcher

A useful annotation has **target → observed problem → consequence → desired change → preserve**. It need not prescribe the code. “The primary action is below review administration, so I have to work out what to do first; prioritize creating the seller link and preserve access checks” carries more judgment than “make this cleaner.”

Batch notes from one journey. Do not send a separate steering interruption for every pixel. But do not save a known wrong product structure for the final polish pass just to protect focus. The rule is whether continuing under the old information makes the result materially worse.

The Head should acknowledge a material input by its disposition, not by a long plan: apply now; after a named checkpoint; proposed next bet; superseded with a reason; or needs your decision. Those dispositions live in the current work record when needed. The team should not ask you to manually reorder every line.

When a decision changes, the Head propagates its revision to affected workers and checks late results before integration. “Frontend done” under an old contract is not permission to restore an old direction. Keep compatible work; invalidate only affected evidence. A status request should not cause all workers to stop and produce reports.

## 3. Goal mode versus ordinary turns

OpenAI's desktop documentation uses `/goal` for multi-step work with an outcome, constraints and completion criteria; the progress row exposes pause, resume, edit and clear. Goal mode retains the same access and approval boundaries. A Markdown file alone is not the host's active goal. [2]

**Use ordinary turns while the next decision is genuinely open:** critique this prototype; compare these two mechanisms; locate the failing boundary; fix this precise text. A finite research question can also become a goal when its source boundary and stopping condition are clear. Goal mode is not reserved for code.

**Use goal mode when you can delegate the result:** finish this joined capability, preserve these constraints, demonstrate these cases, stop at this endpoint. Do not require a fresh prompt for each implementation step. The Head should investigate, build, integrate, test, inspect the rendered result and repair within the existing authority.

The useful contrast is not “big work versus small work.” It is **a delegated outcome with a self-check versus a decision that still needs conversation**. Tiny work does not need long-running machinery. A significant uncertain project needs shaping, not an unlimited “make it excellent” loop.

For your current product work, keep the complete vision and AC-01–07. Make one bounded capability the active bet under it. Example:

> On the current nonlive saved application, finish one ordinary receiving-review journey: inspect source, record the authorized scoped office act, reopen the exact result, and retrieve the correct issued edition through the supported nonlive handoff. Demonstrate a meaningful failure and valid recovery. Preserve buyer funding, identity, authority, history and the selected design. Deliver matching candidate and evidence; label simulations and missing external proof.

This is a proposed bet, not a new adoption or claim that the current route is broken. The [finite goal template](templates/bounded-goal.md) develops it. The [vision goal template](templates/goal.md) keeps all seven acceptance families while making the current bet visible.

## 4. Protect the bet without making the team passive

Use Shape Up's problem, appetite, solution outline, rabbit holes and no-gos only where they resolve uncertainty. The supplied study recommends adapting this for a small team, not importing six-week cycles, a Basecamp migration or a new planning committee. [3, pp. 4, 9–11, 16–24]

Give the Head implementation and sequencing discretion within the current accepted mandate. Do not ask for your permission to rename an internal variable, repair an in-scope form or run an already authorized test. Reserve your decisions for changed promises, material allocation or exposure, real customer evidence, irreversible acts and production release.

A bet ends at its actual evidence boundary. A completed local handoff is not an observed external delivery or a real wire. An accepted checkpoint is not all of AC-01–07. If you delegated sequencing under the umbrella, the Head can choose the next unmet obligation from new evidence within the same authority and resources. Otherwise the result returns a next-bet decision. An optional backlog is not a standing authorization to build forever.

If the authorized investment is exhausted or the route is disproved, reconsider it. Keep accepted obligations owned; do not erase them as old tasks. Cut optional breadth, not truthful saving, privacy or legitimate recovery. Do not invent a duration or token budget just because a template has an appetite field.

## 5. When to check in

Check at the first real joined path, when a decision-changing assumption fails, before reserved exposure and at the accepted endpoint. These are evidence events, not a fixed universal timer. A checkpoint should show what actually works, what remains unproved and the next justified action. It should not become a request to approve routine continuation.

Intervene when the team keeps polishing unconnected surfaces, reruns unchanged checks without a new hypothesis, reports confident completion without matching evidence, or needs you to reconcile every role. Diagnose whether the problem is loading, unclear meaning, unavailable tools, the environment, authority or verification before adding another rule. [4, pp. 51–52]

Measure one next comparable bet: integrated result, unexpected founder interventions, late defects and actual resource use. The test of this edition is a better result with less reconstruction—not more skill files, role messages or tokens. [5, pp. 6–7; 6, pp. 6–7]

## Name the handoff, not just “ship it”

Queue/steer decides when input reaches a run; it does not select the artifact or
authorize a release. Name the endpoint: local prototype, canonical branch preview,
shared-preview acceptance or production decision. An attachment or status question
does not start the next phase.

For the next preview assignment, use wording such as:

> Carry this selected behavior into the canonical app and qualify its exact branch
> preview through our current repository path. Preserve original-feedback coverage
> and the accepted invariants. Show the observed hosted identity, ordinary journey,
> relevant denial and recovery. Do not move shared preview or production.

This is a handoff example, not an authorization already issued. Use existing
permissions instead of repeatedly asking about covered steps. A preview URL is not
proof that the task works, and approval of a source candidate is not evidence that
an environment-specific production build has passed. See
[candidate-bound delivery](references/preview-and-release.md).

## Capture first; close only after both checks

Queue and steer determine when work changes, not whether feedback is retained. Capture every original item and its context before continuing; reload unresolved items after interruption. At acceptance, the existing verifier compares originals against the complete checklist, then exercises the delivered candidate. Keep questions, observations, suggestions and adopted requirements distinct. An FYI is evidence to retain, not permission to resume a paused goal or change policy.
