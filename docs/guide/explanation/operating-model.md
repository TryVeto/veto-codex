# One place to ask; more than one place to think

## The recommendation

Use **one primary pinned coordinator**, on the strongest model you have qualified for
ambiguous, consequential work. Let it commission coherent tasks, preserve the current
bet, synthesize evidence and return decisions to execution. Keep useful domain-manager
conversations, with direct access to their work. They are additional judgment contexts,
not intermediate approval layers.

“One primary conversation” is a convenience for you, not a rule that every task must
queue behind it. Nor is it a promise that one conversation can preserve all company
state forever. Put current commitments and evidence in the relevant working repository
or existing task system. A fresh coordinator must be able to pick them up. A chat is a
replaceable interaction surface, not the sole owner of the company's memory.

The supplied Grokbot interview describes a chief of staff dispatching work to feature
agents, which can manage cloud workers and return PRs with screenshots or videos. That
supports the organizational pattern. It does not demonstrate this Veto package, prove a
particular model mix, or show that a role file transfers a logged-in computer. See the
interview source and qualifications in [Sources](../reference/sources.md).

## Do not make every turn Ultra

Keep the strongest useful model available for the main work, but do not confuse its
model identity with an effort or orchestration setting. OpenAI's current model guide
distinguishes Max's deeper single-task reasoning from Ultra's parallel delegation.
The subagent documentation says unconfigured children inherit parent settings; an
explicit child model without a specified effort can instead use that model's default.
Consequently, “Ultra plus cheap workers” must be configured and observed, not assumed.
[Host sources](../reference/sources.md#current-host-documentation).

My proposed division is simple: strongest qualified judgment for important ambiguity,
architecture and final synthesis; a cheaper qualified worker for bounded, repeatable
execution; a genuinely separate, adequately capable reviewer where independent acceptance
is needed. A difficult implementation may deserve the strongest model too. A routine
lookup may need neither a worker nor maximum effort. Deterministic work should stay code.

**Luna Max is a candidate to test, not a universal worker policy.** Verify that the exact
model/effort combination exists in the actual host. Compare medium and maximum supported
effort on the same task class. Count retries, reviewer repairs, tool/computer usage and
founder interruptions, not just the worker's first response. No model-price claim or
measured savings are made in this edition.

Start with a small batch of comparable authorized tasks. Hold the acceptance test and
available tools constant. Record effective model, effort, task class, first-pass result,
material escaped defects, total observed usage/cost, elapsed time and founder interventions.
Unknown cost stays unknown. Scale the cheaper lane only when it preserves the quality
floor and improves total effort or cost. A critical false acceptance overrides an average
score. Do not spend a week building a benchmark platform for the first comparison.

## Identities should be reusable, not magical

There are five separate objects:

| Object | What it carries | What it does not carry |
| --- | --- | --- |
| Role profile | Responsibility, method, relevant skills, stopping criteria | Credentials or a task claim |
| Model configuration | Engine and supported effort | Expertise proven on every job |
| Run | One actual session, tools and runtime identity | Durable ownership by mere existence |
| Task record | Current scope, revision, owner, evidence and next action | A broader permission than was granted |
| Authority | Permitted operations and reserved decisions | Permission supplied by a persona |

A higher-capability agent can load a domain profile and perform that work. A cheaper
qualified agent can load the same profile for a bounded part. The profile stays stable
while the engine changes. This is the useful meaning of interchangeable identities.

The shipped profiles already exist under `plugins/veto-codex/team/`. Preserve those
charters instead of creating another `roles/` taxonomy. The new index and read-only
context reader make them easy to locate and inspect. `SOUL.md` is optional presentation
or working style; it is not a credential, authorization document or required runtime.

The supplied materials do not define Lunentic's accepted responsibility. This edition
therefore does not invent it. Import its real charter and record a deliberate alias when
that source is available. The generic specialist profile is not proof of Lunentic's job.

## Borrowing expertise is not transferring a live identity

A consultation returns a recommendation to the current owner. A transfer changes who
will finish the task and must preserve its current revision, accepted work, remaining
obligations and actual access. An old writer does not stop merely because a new agent
read the same profile. Reconcile or fence old work before reassigning a shared write path.

Do not switch the builder into the independent-verifier profile and call that independent
acceptance. Use a separate run on the exact artifact and original requirements. Keep
safety constraints visible, avoid seeding the reviewer with a victory narrative, and
disclose shared assumptions. A second model can add useful challenge without creating
an independent factual source.

## Keep persistence where it pays

A domain manager can retain a valuable judgment context. An integration owner may need
continuity through a multi-step delivery. An ephemeral worker can complete one bounded
job and disappear after its result is accepted. A schedule is a trigger, not an identity;
it belongs in the host's actual automation system when authorized.

Prefer your local workflow where it gives observable, reusable state. Use cloud execution
when isolation, concurrency or a needed capability earns the move. A worktree alone does
not isolate ports, browser profiles, databases or credentials. The choice must not turn
into an unrequested platform migration or an assertion that the transcript's cloud
preference has overridden yours.

**The practical test:** you can ask once, inspect the original work when needed, interrupt,
resume through another qualified agent, and receive a usable result. If a growing roster
still requires you to paste context between everyone, the roster has not removed the
bottleneck.
