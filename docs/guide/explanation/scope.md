# What Veto Codex owns

Veto Codex governs work performed through Codex: investigating a problem, designing a
solution, implementing it, checking it, reviewing it, and preserving a handoff. It is
not limited to code generation. Research, product judgment, integrations, and operational
work can use the same discipline without pretending every task produces a pull request.

The name marks a boundary, not a new product brand.

## Three homes, three kinds of truth

**Veto Codex** holds reusable methods, role instructions, offline helpers, and the guide
that explains their choices. Its source is versioned; installed copies are replaceable.

**The working repository** holds application-specific controls, its Feature Map, accepted
assignments, implementation, and evidence. Its actual release and security controls govern
what an agent may do. A source-file checksum is not a bank or deployment authorization.

**Veto’s separate ChatGPT web setup** holds that surface’s management and research
workflows. This package does not rename it, install over it, or require Sebastian to abandon
useful conversations. An explicit handoff may travel between systems with source identity,
accepted scope, relevant decisions, evidence paths, and next owner. Transferring instructions
does not transfer another account’s permissions.

The company and Product Foundations remain sources of direction with their own adoption
status. This operating method does not promote their proposals into agreements or release
permissions. In particular, publishing documentation does not create payment authority.

## Product inspiration is another maintained resource

The supplied reference-library proposal calls for annotated screen references, stable IDs,
provenance, transfer rules, and a generated gallery. That library serves product design;
it is not a reason to copy a full gallery into every Codex context.

Keep its canonical catalog and images with the existing product/reference owner. A Codex
design task should load a small relevant set by ID, preserving what to borrow, what not
to borrow, and what behavior needs proof. A screenshot cannot prove hidden enforcement.

The inherited example sandbox remains here as a labeled fixture, not the live product,
the reference library, or a new product specification. This release does not rebuild
that separate library or silently absorb another plugin.

## Qualification stays with the claim

A guide can be readable before native loading is proved. A helper can pass tests before
an agent uses it reliably. An agent can use the method without a product being ready to
release. Keep those claims separate, and make the next test address the missing one.
